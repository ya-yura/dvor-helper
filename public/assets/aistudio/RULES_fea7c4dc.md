# Правила работы и выпуска

Обновлено: 27.10.2026. Действует вместе с [src/AGENTS.md](src/AGENTS.md) и [client/AGENTS.md](client/AGENTS.md). Пользователь определяет объём задачи; эти правила не дают разрешения на покупки, рассылки или изменение чужих доступов.

## Где менять

| Изменение | Основное место |
| --- | --- |
| Палитра, шрифт, размеры, отступы | `client/src/tokens.css` |
| Общие стили | `client/src/styles.css` |
| Действия, шаги, ошибки и навигация | Общие компоненты `Flow`, `BackNavigation`, `Notice` |
| Карточки, факты и списки | `RecordSummary`, `ReadableList`, `PagedItems` |
| Даты | `src/date-label.ts` + `HumanDate` |
| Права | `src/management/access.ts` и серверные проверки |
| Лимиты | `src/policy.ts`, `services/attachment-policy.ts` |
| Структура данных | Prisma-схема и новая SQL-миграция |

Не исправлять общую проблему отдельными стилями или копией бизнес-правила. Не встраивать CSS в HTML ради обхода проблем доставки. Сначала исправлять общий компонент, токен или источник данных.

## Неизменяемые ограничения

- Изоляция по UUID ЖК, а не названию/адресу. Права и блокировки проверяются сервером заново для каждой операции.
- Только владелец выдаёт управленческие права. Username не является основанием для повторного назначения владельца.
- Подпись Telegram обязательна. Запуск через меню бота или inline `web_app`; неподписанные данные пользователя не заменяют авторизацию.
- Приватные поля доступны отдельно от обычного списка участников. Не публиковать детали заказов в общедоступных каналах.
- Одобрение управляющего и одобрение проживания — разные процедуры.
- Сначала блокировки участников в едином порядке, затем заказа, затем повторная проверка состояния. Сохранять `revision`, идемпотентность и уникальность принятого отклика.
- Изменение управления и его аудит записываются одной транзакцией. Уведомление оформляется через долговечное событие; ошибка доставки не отменяет уже сохранённое действие.
- Сохранять учёт квот и утверждённые правила очистки. Не удалять активные обязательства или открытые споры.
- Не менять `PII_ENCRYPTION_KEY` без отдельного плана перешифрования. Потеря ключа делает зашифрованные данные недоступными.

## Интерфейс

Чёрный фон, системный шрифт, единые токены, текстовые подписи состояний. Одна задача на экран, крупные элементы, явный следующий шаг и возврат с сохранением ввода. Доступность при ширине 320 CSS px и масштабе текста 200%. Цвет не является единственным объяснением состояния. Разрушительные операции подтверждаются, ошибки сохраняют черновик. Полные правила — в контракте клиента.

## Секреты и данные

`.env`, `.runtime`, `data`, дампы, cookie, initData, токены и SSH-ключи не добавлять в документацию, Git и публичные логи. В `.env.example` допустимы только образцы. Не выводить конфигурацию Compose с подставленными секретами. Публичный порт локальной админки запрещён. Резервная копия содержит персональные данные и секреты: хранить с ограниченным доступом, отдельно от сервера.

## Версионирование

В package.json сейчас `0.1.0`; это не подтверждённый номер публичного релиза. На 27.10.2026 рабочая папка не является Git-репозиторием (`git status` завершился соответствующей ошибкой). Не выдумывать коммиты, теги и откат через Git.

До первого управляемого выпуска настроить Git с исключениями для секретов. Рекомендуемая схема: отдельная ветка задачи, осмысленный коммит, версия выпуска и тег. Исправления — patch, совместимые возможности — minor, несовместимые изменения — major. Решение о первом номере выпуска принимается отдельно. Применённые миграции не переписывать: добавлять следующую.

## Подготовка выпуска

1. Установить целевую среду и перечень изменений. Прочитать применимые инструкции.
2. Сохранить резервную копию базы, вложений и конфигурации; записать расположение и возможность восстановления.
3. По запросу пользователя выполнить относящиеся к изменению проверки. Команды доступны в package.json; тесты только в `_test` БД с отдельной схемой, без реальных Telegram-рассылок.
4. Сохранить результат, ограничения и дату в `docs/reports/`. Не выдавать старый отчёт за новую проверку.
5. Подготовить совместимые миграции, образы и способ отката до изменения рабочей установки.

## Выпуск Docker

Подробный ручной порядок: [development-and-release](docs/development-and-release.md). Рабочий `deploy/compose.server.yaml` выбирает образы по `RELEASE_ID`, сохранённому в серверной `.env` и `.current-release`. Обновлять подготовленными одинаковыми образами с `--no-build --pull never`; проверять выбранную версию до запуска. Дополнительный `compose.release.yaml` — шаблон для другой схемы выпуска, не обязательный слой текущей установки. `deploy/update-server.sh` сохраняет предыдущие образы, backup и счётчики существующих сущностей перед добавочной миграцией; не восстанавливает старую БД автоматически.

Типовая команда для подготовленной среды: `docker compose up -d --build --wait`. Это изменяет работающую систему; не запускать в задачах только по текстам. API выполняет `prisma migrate deploy` при старте. Worker должен иметь доступ к тем же вложениям, что API.

После выпуска проверить `docker compose ps`, `/health/ready`, HTML и его фактические JS/CSS, авторизованный вход и затронутую операцию. HTTP 200 страницы не доказывает работоспособность приложения. Хранить старые хешированные assets для открытых WebView; HTML — `no-store`, отсутствующие assets — 404. Не удалять том `client_assets`.

## Перенос и откат

Сначала подготовить сервер и HTTPS, затем коротко остановить запись в старую установку, сделать финальный дамп и копию вложений, восстановить и сверить данные. Должен работать один Telegram polling-процесс. Нельзя допустить независимую запись в две базы. Переключить меню Telegram и проверить реальный вход. Отключить старый supervisor только после успешного переключения.

При ошибке остановить новые записи и polling, определить, появились ли новые данные. Простой возврат старого образа допустим лишь с совместимой схемой. Восстановление старой БД после новых записей требует отдельного согласованного плана сохранения этих записей. Не использовать `docker compose down -v`, `migrate reset`, удаление рабочих томов и слепой повтор миграций как способ ремонта.
