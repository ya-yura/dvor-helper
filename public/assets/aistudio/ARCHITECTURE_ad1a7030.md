# Техническая схема

Срез исходников: 27.10.2026. Это описание реализации, не результат новой проверки работающего сервера.

## Компоненты

```text
Telegram → Mini App → публичный HTTPS → nginx
                                      ├─ /, /assets/ → client (React/Vite)
                                      └─ /api/, /health/ → app (Fastify)
Telegram Bot API ← long polling / grammy ──────────────┤
                                                     ├─ PostgreSQL / Prisma
                                                     ├─ Redis / BullMQ
                                                     └─ локальные вложения или S3
worker → DeferredEvent / очереди → уведомления, завершение, очистка

Браузер владельца → 127.0.0.1:8090 local-admin → локальный nginx
```

На компьютере публичный HTTPS обеспечивает временный localhost.run. В Compose постоянного TLS-терминатора нет. Облачная установка не завершена. Local-admin сейчас рассчитан на локальные API и БД; перенос требует адаптации.

| Компонент | Технология / точка входа |
| --- | --- |
| Клиент | React 19, TypeScript, Vite, React Query; `client/src/App.tsx` |
| API и бот | Node.js, Fastify 5, grammy; `src/server.ts`, `src/app.ts`, `src/bot/` |
| Worker | BullMQ, Redis, периодические сканирования; `src/worker.ts` |
| База | PostgreSQL 16, Prisma 6.19; `prisma/schema.prisma` |
| Файлы | `LocalStorageService` либо приватный S3 через AWS SDK |
| Прокси | nginx; `nginx/default.conf` |
| Локальный запуск | `scripts/run-local.mjs`, PowerShell/VBS launcher |

Корневой package.json требует Node ≥20.19; Dockerfile использует Node 22. Конкретные зависимости и команды определяют lock-файлы и package.json соответствующего пакета.

## Сеть Compose

Сервисы: `postgres`, `redis`, `app`, `worker`, `client`, `nginx`; `postgres-test` включается профилем `test`. Снаружи локально доступны nginx `127.0.0.1:8080`, PostgreSQL `127.0.0.1:55432`, Redis `127.0.0.1:56379`. Тестовая БД — `127.0.0.1:55433`. API внутри сети слушает 3000; при отдельном dev-запуске адрес определяется HOST/PORT.

Тома: `postgres_data`, `redis_data`, `client_assets`. Каталог `data/uploads` смонтирован в app и worker. Привязку приватных портов к loopback сохранять на сервере. Nginx использует DNS Docker для обновляемых upstream.

## Модель данных

| Группа | Модели и назначение |
| --- | --- |
| Участники | `User`, `ExecutorProfile`, `Location`: Telegram-идентичность, услуги исполнителя, снимок адреса |
| Пространства | `ResidentialComplex`, `ComplexMembership`, `ManagementGrant`, `ComplexBan` |
| Подключение | `ManagerApplication`, разрешение создания в User, проверка ЖК с revision |
| Публикации | `Category`, `Order`, `ServiceOffer`, `Bid` |
| Результат | `Review`, `Complaint`, `PaymentTransaction` |
| Управление | `ManagementAudit`, `SystemConfig` |
| Доставка | `DeferredEvent`: долговечные события в БД |
| Вложения | `Attachment`, `UploadLedger` |
| Очистка | `RetainedReputation`, `RetainedDemand`, `OrderReceipt`, `RetentionFile` |

Связь заказа с ЖК проходит через Location. У заказа сохраняется снимок адреса; переезд не переписывает историю. Telegram ID — bigint, деньги — Decimal. Не выполнять денежную арифметику через неточный JS number. Номер телефона и приватная часть адреса зашифрованы AES-GCM; ключ вне БД, контекст защищает от перестановки шифротекста между записями.

## Авторизация и области доступа

`src/auth/init-data.ts` проверяет подписанные Telegram initData. Авторизация не доверяет полям пользователя из браузера. После идентификации сервер проверяет текущий аккаунт, бан, членство и разрешения. Управленческие проверки — `src/management/access.ts`.

`User.role=ADMIN` — глобальный владелец. `ManagementGrant` — конкретные разрешения на конкретный UUID ЖК. Обычные возможности требуют APPROVED-членства; управленческий доступ независим от проживания. `members.private` отдельно разрешает телефон и полный адрес. Смена названия не меняет область доступа.

Local-admin выдаёт короткий одноразовый вход, затем HttpOnly/SameSite=Strict cookie; проверяет Host/Origin и использует существующего единственного ADMIN. Его служебная подпись остаётся на gateway. Порт 8090 не публикуется.

## Сделка и конкуренция

Основной путь без платформенных платежей:

```text
SEARCHING → выбор одного отклика → IN_PROGRESS
          → запрос завершения → подтверждение → COMPLETED
Активная сделка → спор → DISPUTED → решение по правилам сервиса
Допустимая отмена → CANCELED
```

`AWAITING_PAYMENT` используется включаемым отдельно платёжным потоком. В выключенном режиме деньги передаются напрямую между сторонами.

Перед решением сервер блокирует участников в отсортированном порядке, затем заказ; повторно читает состояние, членство, версию и выбранные условия. `Order.revision` повышается триггером. Частичный уникальный индекс не позволяет принять два отклика. Устаревшая операция получает конфликт вместо молчаливого перезаписывания результата.

Создание заказа использует Idempotency-Key и хеш полезной нагрузки. Повтор после потерянного ответа возвращает прежний результат; изменение содержимого требует нового ключа. Клиент сохраняет черновик и ключ при неоднозначном исходе. После 409 обновляет данные, не повторяет мутацию вслепую.

## Уведомления и завершение

Событие сохраняется вместе с бизнес-операцией в PostgreSQL (`DeferredEvent`). Worker доставляет с повторениями, lease и backoff; потребители должны выдерживать дубликаты. Перед отправкой проверяются актуальные права и состояние. Redis используется для очередей и задержанных задач, но не заменяет основную БД.

Для прямого расчёта после запроса завершения предусмотрены напоминания и автоматическое завершение через 24 часа по правилам сервиса. Worker дополнительно сканирует просроченные запросы независимо от задержанных Redis-задач. Без TELEGRAM_BOT_TOKEN текущий worker остаётся idle: очистка истории в таком запуске тоже не стартует.

## Файлы, лимиты и очистка

Константы — `src/policy.ts`: одно вложение, 5 MiB на файл, 30 MiB за скользящие 7 суток, 21 заказ за тот же период. API принимает изображения допустимых форматов; это не универсальное файловое хранилище. Проверяются сигнатуры, принадлежность и привязка вложения. STAGED-вложение имеет ограниченный срок привязки. Подписанная ссылка даёт временный доступ; каталог не должен раздаваться открыто.

`SEARCHING` с наступившим executionDate исключается из свободной ленты; срок не назначается автоматически объявлениям без даты. Активные принятые сделки сохраняются. Через 30 дней после закрытия worker удаляет завершённые/отменённые сделки без открытого спора и незавершённого платежа, сохраняя агрегаты рейтинга и минимальную квитанцию. Физические файлы удаляются через повторяемую очередь. Политика подробно описана в [order-retention](docs/order-retention.md).

## Спрос и интерфейс

`category-demand.ts` оценивает 90 дней, сильнее учитывает последние 30, ограничивает вклад участника и исключает неподходящие публикации/блокировки. Кеш ограничен 100 ЖК на 15 минут. Клиент сохраняет выданный порядок в ходе выбора; не получает приватные счётчики.

Токены — `client/src/tokens.css`; компоненты — Flow, BackNavigation, RecordSummary, ServicePicker. Assets публикуются атомарно и остаются в постоянном томе для старых WebView. Нельзя исправлять доставку CSS копированием всей темы в HTML.

## Эксплуатация и ограничения

Секреты задаются окружением; список имён — `.env.example`, валидация — `src/config.ts`. Текущий публичный адрес локального запуска находится в `.runtime/public-url.txt` и `SystemConfig.public.webAppUrl`; supervisor синхронизирует меню Telegram. Резервирование — `scripts/backup-local.ps1` (дамп, .env, uploads). Для финального переноса нужна остановка записей: обычная горячая копия БД и файлов не гарантирует единого момента снимка.

Сейчас нет подтверждённого отказоустойчивого кластера, завершённого облачного выпуска, настроенного платёжного провайдера и доказанной нагрузки десятков тысяч ЖК. `/health/ready` не проверяет доставку Telegram, доступность внешнего HTTPS, диск и восстановимость резервной копии.
