# Сервис заказов для жилых комплексов

Telegram Mini App и бот для заказов внутри жилого комплекса. Стек: React, Fastify, PostgreSQL, Prisma, Redis, BullMQ и приватное S3-хранилище.

## Запуск

Требуются Node.js 20.19+ (рекомендуется актуальная LTS) и Docker Compose.

```powershell
npm ci
Copy-Item .env.example .env
node -e "console.log(require('node:crypto').randomBytes(32).toString('base64'))"
```

Вставьте полученный ключ в `PII_ENCRYPTION_KEY` в `.env`. Не добавляйте `.env` в Git. В подготовленной локальной среде `.env` уже создан с отдельным случайным ключом; сохраняйте его, чтобы не потерять доступ к зашифрованным адресам.

```powershell
docker compose up -d --wait
npm run db:generate
npm run db:migrate
npm run dev
```

API: `http://127.0.0.1:3000`. `GET /health/live` проверяет процесс; `GET /health/ready` проверяет PostgreSQL и Redis (503 при недоступности). Ответы содержат `x-trace-id`. Запросы получают серверный UUID независимо от входящих заголовков. SIGINT/SIGTERM закрывают HTTP-сервер и подключения.

Полный Docker Compose стек (API, worker, PostgreSQL, Redis, client и Nginx): настройте `.env` и выполните `docker compose up -d --build --wait`. Для Telegram задайте `TELEGRAM_BOT_TOKEN`, публичный HTTPS `TELEGRAM_WEB_APP_URL` и список `JK_NAMES`. После запуска администратор может менять список ЖК в панели. Для фото задайте приватный S3-совместимый бакет и его credentials. Веб-интерфейс доступен на `http://127.0.0.1:8080` (порт задаётся через `HTTP_PORT`).

Для сборки: `npm run build`, затем `npm start`. Локальные контейнеры PostgreSQL и Redis привязаны только к loopback. Пароли в Compose предназначены для разработки.

## Проверки

```powershell
docker compose --profile test up -d --wait
npm run db:validate
npm run typecheck
npm test
npm run test:e2e
npm run build
npm --prefix client test
npm --prefix client run build
npm audit
```

`npm run test:unit` не требует внешних сервисов. `npm run test:db` выполняет интеграционные тесты из `tests/infrastructure/db.test.ts`. Нужен `TEST_DATABASE_URL` из `.env.example`: отдельная БД с именем, заканчивающимся на `_test`. Отсутствие настройки приводит к ошибке, а не к пропуску тестов.

Каждый запуск создаёт случайную схему `test_<uuid>`, применяет миграции и удаляет только эту схему после тестов. Рабочая БД не очищается. Тестовая БД в Compose использует tmpfs и теряет данные после остановки контейнера.

Проверяются CRUD пользователя и адреса, весь граф связей, m2m категорий исполнителя, точность денег и Telegram ID, уникальность отклика и внешнего платежа, внешние ключи, запрет некорректных сумм и оценок, подмена шифротекста/ключа/контекста, traceId и отсутствие чувствительных данных в проверяемых логах.

## Структура

- `prisma/schema.prisma` — модели, enum, индексы и связи.
- `prisma/migrations/` — начальная миграция и SQL CHECK-ограничения.
- `src/app.ts` — фабрика Fastify и health endpoints.
- `src/server.ts` — загрузка настроек, подключения и завершение процесса.
- `src/infrastructure/` — Prisma, Redis и Pino.
- `src/security/pii.ts` — шифрование и аутентифицированная расшифровка.
- `src/repositories/location.ts` — запись зашифрованного адреса.
- `tests/` — модульные и интеграционные тесты.

## Данные и безопасность

`telegramId` и `channelTelegramId` используют PostgreSQL BIGINT / JavaScript bigint. В будущих DTO их нужно сериализовать строками. Денежные поля используют Decimal(12,2); передавайте суммы строками, без арифметики через JS number. Валюта текущего этапа — RUB по соглашению; мультивалютность ещё не реализована.

`BudgetType`: FIXED, RANGE с минимальной и максимальной суммой или NEGOTIABLE. `ComplaintStatus`: OPEN, IN_REVIEW, RESOLVED, REJECTED. Рейтинги 0–5 (0 означает отсутствие оценок), оценка отзыва 1–5. Уникальность `telegramId` сама создаёт индекс; дополнительно созданы требуемые составные индексы. Удаление записей, на которые ссылаются заказы и платежи, запрещено внешними ключами.

`LocationRepository` принимает `{ flat, entrance?, floor? }` и сохраняет JSON только внутри `flatEncrypted`. Конверт имеет вид `v1.<nonce>.<tag>.<ciphertext>` (base64), nonce — 12 случайных байт, tag — 16 байт. AAD `Location:<id>:flatEncrypted` защищает от переноса шифротекста между записями. Операции репозитория возвращают только `id` и `jkName`.

`building` хранится отдельно; корпус показывается исполнителю, квартира остаётся закрытой до выбора. Номер телефона шифруется тем же AES-GCM слоем и расшифровывается только при обмене контактами между сторонами сделки. При смене адреса создаётся новая запись Location, поэтому старые заказы остаются на прежнем адресе. Ключ хранится вне БД. Версионирование конверта предусмотрено; ротация ключей ещё не реализована.

Pino пишет JSON с `context`, `traceId` и `err.stack` для ошибок. Вне HTTP-запроса `traceId` равен null. HTTP-логи не включают query, заголовки, тело и IP; известные структурированные поля PII скрываются. Маскирование не распознаёт секреты в произвольных сообщениях и глубоко вложенных объектах: не передавайте в logger целые записи БД или произвольный пользовательский текст. Ошибки обработчиков HTTP очищаются перед логированием.

## Текущие возможности и границы релиза

Интерфейс поддерживает регистрацию с ролями, профиль исполнителя и категории, создание заказов с датой, фото и тремя форматами бюджета, ленту по ЖК, отклики и их отзыв, выбор мастера с атомарным отклонением остальных, обмен контактами, отмену и повторную рассылку, завершение, жалобы, отзывы и админ-панель. Администратор может управлять списком ЖК, просматривать статистику и жалобы, разбирать споры, блокировать и разблокировать пользователей. После запроса о выполнении заказчику отправляются напоминания через 12 и 22 часа; при отсутствии ответа через 24 часа заказ автоматически завершается.

Платежи выключены по умолчанию (`PAYMENT_ENABLED=false`): цена фиксируется в сделке, контакты передаются сторонам, заказ начинается, а расчёт происходит наличными напрямую между сторонами. Таблицы и код платформенных платежей сохранены за флагом.

Поток с оплатой через платформу (`PAYMENT_ENABLED=true`) требует подключения платёжного провайдера для создания платежей, возвратов и выплат. Без него остаётся рабочий сценарий оплаты наличными между участниками. Для запуска Telegram Mini App настройте HTTPS `TELEGRAM_WEB_APP_URL`; для загрузки фотографий — приватное S3-хранилище.

Для платформенных платежей задайте `PAYMENT_ENABLED=true`; это переводит выбор исполнителя в `AWAITING_PAYMENT`. Подключите и проверьте провайдера, ключи, webhook и capture/payout до использования этого режима. Для тестов используется отдельная PostgreSQL БД с суффиксом `_test`; E2E создаёт и удаляет отдельную схему.

## Фильтрация контактов и изображения

`sanitizeText(text)` из `src/services/anti-contact.service.ts` возвращает `{ isClean, sanitizedText, detectedTypes }`. Категории: `phone`, `telegram`, `link`, `address`; найденные фрагменты заменяются на `[REDACTED]`. Проверяются последовательности от семи цифр, в том числе отдельные цифры русскими словами и смешанная запись, `@username`, HTTP(S), t.me/telegram.me, www-ссылки, числа рядом с обозначениями квартиры, дома, корпуса, подъезда или улицы. Перед проверкой выполняется NFKC-нормализация и удаление невидимых форматирующих символов. Чистый текст возвращается без изменений. Перекрывающиеся совпадения объединяются, категории не повторяются.

Это эвристика: произвольные шифры, составные числительные и контакты на изображениях не распознаются; длинные числовые последовательности могут дать ложное срабатывание. Короткие числа без адресного контекста не блокируются. Вызывающий код должен отклонять сообщение при `isClean === false` либо сохранять только `sanitizedText`; сам модуль ничего не сохраняет и не логирует.

```ts
import { createStorageService } from './src/services/storage.service.js';

const storage = createStorageService(); // S3_* из окружения
try {
  const { key } = await storage.uploadImage({ buffer: imageBuffer, mimeType: 'image/png' });
  // Сохраните key. Проверьте права пользователя перед выдачей ссылки.
  const url = await storage.generateSignedUrl(key);
} finally {
  storage.destroy(); // В сервере вызывается при завершении процесса.
}
```

Настройки описаны в `.env.example`: `S3_BUCKET`, `S3_REGION`, опциональные `S3_ENDPOINT`, `S3_ACCESS_KEY_ID` и `S3_SECRET_ACCESS_KEY`. Для AWS можно использовать стандартную цепочку credentials SDK (включая IAM role); для R2 задайте endpoint аккаунта, регион `auto` и оба ключа. Настройки проверяются только при создании сервиса, поэтому существующие health endpoints не требуют S3.

Загрузка принимает Buffer размером от 1 байта до 10 × 1024 × 1024 байт включительно. Разрешены только `image/jpeg`, `image/png`, `image/webp`, дополнительно проверяется сигнатура формата (это не полное декодирование изображения). Случайный UUID определяет ключ `images/<uuid>.<extension>`. Бакет должен быть приватным; сервис не устанавливает публичные ACL. Ссылки GET подписываются на 900 секунд, при временных AWS credentials доступ может закончиться раньше. Порядок настройки и подписи соответствует [документации Cloudflare R2 для AWS SDK v3](https://developers.cloudflare.com/r2/examples/aws/aws-sdk-js-v3/).

`tests/services/anti-contact.test.ts` проверяет фильтрацию, загрузку через замоканный S3 transport, отклонение файлов и реальные подписи SDK с тестовыми ключами для AWS/R2. Запуск: `npm run test:unit` или `npx vitest run tests/services/anti-contact.test.ts`. Облачный бакет тестам не нужен. HTTP-маршруты загрузки и проверка прав остаются задачей вызывающего приложения.

Prisma 6.19 закреплена для выбранной структуры клиента и datasource в schema.prisma ([документация Prisma 6](https://docs.prisma.io/docs/orm/v6/reference/connection-urls)). В `overrides` задан deepmerge-ts 8.0.0 для зависимости CLI `@prisma/config`, чтобы устранить уязвимость предыдущей версии; генерация и миграции проверяются с этой зависимостью. При обновлении Prisma пересмотрите override. Fastify использует `loggerInstance` ([документация](https://fastify.dev/docs/latest/Reference/Server/)).
